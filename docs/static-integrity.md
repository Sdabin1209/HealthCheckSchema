# 정적 계약 검사에서 확인하는 관계

이 문서는 JSON Schema의 구조 검사에 더하여 검사하는 자료 내부 관계와 검증 완료 정보의 역할을 설명한다. 업무 판단·상태 전이·DB 반영을 실행하지 않는다. 계약 JSON의 새 필드나 운영 한도를 추가하는 문서가 아니다.

## 식별 키의 범위

| 자료 | 유일해야 하는 키 | 필요한 이유 |
|---|---|---|
| QuestionBank.questions | question_id | ID로 조회한 문항 정의가 하나로 결정되어야 함 |
| QuestionDef.slots | 해당 문항 안의 slot_id | 문항 ID와 함께 답 칸을 식별해야 함; 다른 문항의 같은 슬롯 ID는 허용 |
| SessionStore.answer_records | 해당 상태 안의 (question_id, repeat_key, slot_id) | 한 슬롯의 현재 응답 기록을 하나로 결정해야 함; 다른 반복 행은 다른 키 |

이 검사에는 문항 수의 상한이나 특정 문항·코드 목록이 없다. 식별자의 기존 의미를 무결성 검사에서 확인하는 것이다. `uniqueItems`만으로는 키가 같고 다른 필드가 다른 행을 구별하지 못하므로 키를 직접 비교한다. 의미와 필요 이유는 해당 필드의 fields·semantics 원본에도 명시한다.

## 모든 예시의 무결성

`check_information_integrity.py`는 valid로 선언된 schema_examples와 모든 case_shapes의 specimens를 검사한다. T 접두사를 가진 케이스만으로 제한하지 않는다. 같은 payload는 검사 결과를 재사용하되 모든 원천 예시에 결과를 연결한다. 보고서의 specimens는 전체 검사 대상 수, unique_payloads는 중복을 제외한 payload 수다. unique_payloads를 별도로 기록하는 이유는 결과 재사용이 검사 대상 누락으로 오인되지 않도록 검사량과 원천 예시 수를 구분하기 위해서다. span 위치·구절 길이, 선택지 코드 중복·참조, 문제 분류, 조회 버전 관계와 위 식별 키를 확인한다.

원문의 실제 해당 위치와 구절이 같은지, 답의 해석이 맞는지 등 업무 판단은 하지 않는다. JSON Schema 단독 검사와 이 추가 무결성 검사는 구분한다.

## 출력에서 저장 상태로 보내는 자료

`check_handoffs.py`는 필드의 존재·근거와 전달 방식별 payload/state 타입 관계를 확인한다.

| 방식 | 확인하는 관계 | 이유 |
|---|---|---|
| append_record | 원천의 비-null 자료형과 목적 배열의 항목 자료형이 같음 | LogEntry를 DispatchRecord 배열에 잘못 연결하는 오류 방지 |
| create_record | 원천의 비-null 자료형과 목적 기록 자료형이 같음 | 생성할 기록의 구조와 보관 구조를 맞춤 |
| write_update | 동일 자료형 또는 명시된 ProgressRecordUpdate → ProgressRecord 관계 | 갱신 자료와 현재 상태는 다른 형태일 수 있음 |
| write_decisions | StoreDecision 배열 → SlotRecord 배열의 명시된 관계 | 저장 결정은 현재 기록과 같은 값의 직접 복사가 아님 |

null은 자료 미제공을 표현하므로 최외곽의 null 분기를 제외하고 payload를 비교한다. 현재 검사는 동일한 구조 선언·참조와 위 명시된 변환 관계를 대상으로 하며 일반적인 모든 JSON Schema 간 포함 관계를 증명하는 도구가 아니다. 새 변환 관계가 필요하면 그 의미·근거·검사 규칙을 함께 정의한다. 갱신·결정을 실제 상태에 적용하거나 반영 결과를 계산하지 않는다.

## 생성 기준과 검증 완료를 구분

`generated/source_manifest.json`은 생성 당시 원본 버전·해시이며 전체 검사 성공의 증거가 아니다. `generated/verification_result.json`은 `verify.py`의 모든 검사와 회귀 테스트가 통과한 후에만 원자적으로 기록된다. 검증 시작과 독립적인 build 실행은 이전 성공 기록을 삭제한다. 도중 실패하거나 원본·검사기가 바뀌면 성공 기록을 만들지 않는다.

| 검증 완료 파일의 항목 | 의미와 필요한 이유 |
|---|---|
| status | 전체 정적 검사가 passed인지 표시; 생성 완료를 성공으로 오인하지 않기 위해 필요 |
| contract_version | 검사한 계약 버전; 현재 기준 버전과 대조하기 위해 필요 |
| source_sha256 | 검사한 계약·요구·예시·규칙의 지문; 원본 변경 뒤 과거 결과를 재사용하지 않기 위해 필요 |
| checker_sha256 | 검사기·생성기·테스트·의존성 선언 파일의 지문; 검사 코드 변경 뒤 과거 결과를 재사용하지 않기 위해 필요 |
| artifacts_sha256 | 검사된 배포 Schema·연결/상세 문서·보고서의 지문; 생성물 수정·삭제·추가를 감지하기 위해 필요 |
| completed_at | UTC 완료 시각; 성공 기록이 언제 작성됐는지 추적하기 위해 필요하며 시각만으로 유효성을 판단하지 않음 |

`python3 verify.py --check`는 저장된 결과의 상태·버전과 원본·검사기·생성물 지문을 대조한다. 불일치·기록 부재 시 실패하므로 전체 verify를 다시 실행한다. 이 명령은 검사를 다시 실행하는 대신 마지막 성공 결과가 현재 파일과 같은 대상을 가리키는지 확인한다. 사람용 웹 데이터 생성도 이 확인을 통과해야 한다.

로그 파일·이 완료 파일 자체는 생성물 지문에서 제외한다. 완료 파일이 자기 자신을 해시하는 순환과 로그 갱신 때문에 결과가 무효화되는 일을 피하기 위해서다. 검사기 지문은 요구된 의존성 선언을 포함하지만 설치 환경의 모든 바이너리나 실행 성능을 인증하지 않는다. 성공 기록은 암호학적으로 서명된 보안 인증서가 아니다.
