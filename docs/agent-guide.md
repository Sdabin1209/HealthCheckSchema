# 에이전트의 구조·계약 탐색과 구현 준비

이 문서는 이 저장소에서 필요한 구조와 계약을 찾는 방법을 설명한다. 데이터 계약을 지키는 구현의 시작점이며, 업무 동작 전체가 구현 가능하거나 검증됐다는 선언은 아니다.

## 탐색 범위

스키마·업무 컴포넌트 작업에서 `presentation/`은 제외한다. 이 경로의 Svelte 컴포넌트·HTML·generated-data.json은 사람용 웹의 구현·생성물이므로 계약이나 업무 코드의 원본으로 사용하지 않는다. 의존성·캐시도 읽지 않는다. 웹 작업을 명시적으로 요청받았을 때만 별도 웹 README로 진입한다.

## 목적별 시작점

| 알아야 하는 것 | 시작점 | 다음 참조 |
|---|---|---|
| 저장소의 목적·범위·파일 책임 | 루트 README | 이 문서와 구조 문서 |
| 전체 컴포넌트 책임·처리 순서 | `docs/architecture.md` | `work/contracts/components.yaml` |
| 어느 출력·상태가 어느 입력으로 전달되는가 | `work/out/connections.md` | `bindings.yaml`, `output_bindings.yaml` |
| 컴포넌트의 입출력 계약명 | `work/schema.md` | `work/out/components/<component_id>.md` |
| 계약·타입의 실제 원본 위치 | `work/contracts/manifest.yaml` | 지정된 schema·semantics 파일 |
| 필드의 의미·필요 이유·근거 | 해당 fields·semantics | case_refs에 해당하는 요구사항 |
| 동작을 설명하는 관련 요구 | `work/rules/README.md`, `manifest.yaml` | 해당 컴포넌트·시점·원칙 문서 |
| 입력·출력의 완전한 JSON 예시 | `work/testcases/schema_examples/<계약명>.json` | 해당 계약의 원본 Schema |
| 특정 상황의 정보와 예시 | `work/testcases/case_shapes/<케이스ID>.json` | 요구사항 manifest·cases, assertions의 원본 포인터 |
| 외부 구현에서 사용할 자체 완결 Schema | `generated/schemas/INDEX.md` | standalone의 계약 파일 |
| 추가 자료형 제안 | `work/contracts/proposals.yaml` | proposals의 Schema; 현행 계약과 구분 |

경로는 저장소 루트를 기준으로 한다. 구조·의미·생산 소비 책임의 우선순위는 `work/contracts/README.md`에서 확인한다. 상세 문서가 원본과 다르면 생성물을 임의의 새 계약으로 취급하지 않는다.

## 전체 흐름을 파악하는 법

먼저 구조 문서에서 역할을 확인하고, 연결 인덱스에서 목적 컴포넌트의 입력과 생산 컴포넌트의 출력을 양방향으로 추적한다. 인덱스의 행에는 양쪽 계약·필드, 시점, 전달 방식과 현행/제안 구분이 있다. 같은 저장 상태라도 읽는 시점이 다르면 같은 값이라고 가정하지 않는다.

이 연결은 논리적인 생산·소비 관계다. 실제 호출·조회·입력 조립·전달은 Orchestrator의 책임이다. 저장 갱신·결정 자료를 저장 상태로 보내는 선언은 값의 직접 복사나 반영 성공을 뜻하지 않는다. 호출 프로토콜·구현 언어·네트워크·DB 서버 구성을 이 인덱스에서 추론하지 않는다.

## 컴포넌트 하나의 코드를 요청받았을 때

1. components.yaml에서 해당 컴포넌트의 책임과 입력·출력 계약, 상태·Trace 및 제안 여부를 확인한다.
2. manifest에서 계약 원본과 설명을 찾는다. 구조는 Schema를 읽고 `$ref`로 필요한 공통 타입만 따라간다. 선택 필드, null, 빈 배열의 차이와 조건 분기를 확인한다.
3. 연결 인덱스와 bindings에서 입력의 원천·시점·투영·결합 방식, 출력의 소비·저장 목적을 확인한다. 담당 컴포넌트 밖의 책임을 구현 안으로 가져오지 않는다.
4. 해당 역할의 업무 요구와 필드 case_refs에 연결된 케이스를 읽는다. 예시는 구조와 표현 위치를 보여주는 재료이며 모든 입력의 동작 명세를 대신하지 않는다.
5. 알고리즘·선택 정책·실패 처리 등 필요한 동작이 미정의이거나 충돌하면 해당 위치와 영향을 명시한다. 모르는 동작을 예시 하나에서 일반화하거나 임의로 정책을 확정하지 않는다. 정의된 부분은 구현하되 미정의 부분을 구현 완료로 보고하지 않는다.
6. 정해진 입출력 계약을 유지한다. 데이터가 맞지 않는다는 이유로 필드·코드·타입·책임을 임의로 바꾸지 않는다. 계약 변경이 필요하면 요구·원본·의미·예시를 함께 수정하는 별도 변경으로 다룬다.
7. 구현 입출력을 해당 JSON Schema로 검사하고, 필드 의미·책임·정보 보존을 확인한다. 업무 동작 검사는 구현 프로젝트에서 수행하고 이 저장소의 정적 검사 결과와 구분해 보고한다.

모델 컴포넌트는 이 문서만으로 학습 가중치나 예측 성능이 제공되는 것이 아니다. 모델 호출 경계와 계약을 구현하는 것, 실제 발화 해석·응답 성능을 달성하는 것은 구분한다.

## 검증의 한계

`python3 verify.py`는 계약 원본·생성물·참조·정적 예시의 구조와 선언된 정보 관계를 검사한다. 실제 모델·업무 컴포넌트·DB를 실행하지 않는다. 생성물을 검사 완료 자료로 사용하기 전 `python3 verify.py --check`로 현재 원본·검사기·생성물과 마지막 성공 결과의 일치를 확인한다. 실패하면 전체 verify를 실행한다. 이 명령의 통과를 구현 동작의 성공이나 모든 업무 정책의 완전성으로 보고하지 않는다.

AGENTS.md와 문서 안내는 에이전트가 올바른 원본과 범위를 찾도록 돕는 지침이다. 에이전트가 반드시 지침을 읽거나 모든 명세를 준수한다는 강제 장치는 아니다. 구현을 검토하고 필요한 실행 검사를 수행해야 한다.
