# 검증 방법과 결과의 의미

검증 목적은 요구사항에 필요한 정보를 현재 계약으로 표현할 수 있는지 확인하는 것이다. 고정 데이터와 Schema를 대조하며 업무 컴포넌트를 실행하지 않는다.

## 검사 단계

| 단계 | 확인하는 내용 | 결과 |
|---|---|---|
| 원본 검사 | 중복 ID·키, Schema 문법, 필드 설명, 요구·입력 출처 참조 | 오류가 있으면 실패 |
| 생성·대조 | 원본과 배포 Schema·문서·요구자료의 일치 | 오류가 있으면 실패 |
| 경계 예시 검사 | 완전한 정형 예시와 허용·거부 조합 | 선언한 허용 결과와 다르면 실패 |
| 케이스별 표현 검사 | 원문 요구의 표기 보존, 담당 필드, 완전한 예시, 정보 누락 | 정보 손실·구조 위반이면 실패 |
| 정적 전달 검사 | 고정된 원천·목적 예시의 필드 연결과 정보 보존 | 연결 오류·값 손실이면 실패 |
| 자료 무결성 검사 | 근거 위치 단위·선택지 코드·문제 분류·조회 revision의 내부 관계 | 정적 자료가 조건과 다르면 실패 |
| 회귀 검사 | 구조 위반·누락·참조 오류 등의 검출 | 검사 결과가 예상과 다르면 실패 |

정답 코드 선택, 자연어의 공감·진단 여부, 질문 순서, DB 저장 효과, 실제 전달 성공은 이 검사에 포함되지 않는다. `ANSWERED`와 `UNKNOWN`이 모두 허용된 계약이라면 두 값 모두 형식상 유효할 수 있다.

## 정적 예시를 읽는 방법

`case_shapes/<ID>.json`의 specimens는 계약별 완전한 데이터 예시다. requirements는 케이스의 정보가 어느 예시의 어느 필드에 들어가는지 연결한다. 정형 값의 표기 차이는 `case_notation.yaml`에 명시한다. 요구사항 해시가 바뀌면 예시를 재검토해야 한다.

모든 specimens를 이어 붙이면 검증된 E2E Trace가 된다고 해석하지 않는다. 검사기는 케이스 전체의 상태 전이, 모든 출력과 다음 입력의 일치, 저장 효과를 증명하지 않는다. 예시의 role·turn과 원천 시점이 다르면 같은 계약도 값이 다를 수 있다.

SessionStore 예시의 `initial_state`는 초기 상태, `processing_state`는 처리 중 상태, `final_state`는 최종 상태 예시라는 분류다. processing_state라는 이름만으로 저장 반영 후라고 판단하지 않는다. 실제 구현에서는 bindings의 snapshot에 맞는 값을 수집한다.

`handoff_examples.json`은 지정한 필드 전달만 비교하는 완전한 원천·목적 예시다. 이 검사에 통과한 필드 연결과 검사하지 않은 선택·변환 조합을 구분한다. `schema_examples/TurnTrace.json`도 실행 결과가 아닌 형태 예시다.

## 요구 성격에 따른 처리

선언한 코드·수치·대상은 그 정보를 표현하는 필드와 값 보존을 확인한다. 존재·부재 및 빈 확인 대기는 null·빈 상태 예시와 대조한다. 산문 내용 요구는 해당 내용을 담을 필드와 연결하며 의미의 진위를 판정하지 않는다. 상태 보존·변경 요구는 상태와 로그의 표현 위치를 연결하며 전이 로직을 실행하지 않는다.

## 결과의 적용 범위

[VERIFIED.md](../VERIFIED.md)는 검사 결과 요약이고 `generated/*report.json`은 상세 결과다. 통과는 선언한 예시가 해당 검사에 통과했다는 뜻이다. 모든 업무 분기, 모든 입력 조합, 미래 문항, 필드의 최소성까지 증명하지 않는다. [추가 계약 제안](../work/contracts/proposals.yaml)은 현행 계약과 별도로 구분한다. 테스트 데이터의 개수나 실제 코드 목록은 스키마 완성 조건이 아니다.

JSON Schema만으로 확인하지 않는 근거 위치의 수치 관계와 코드 참조·버전 관계는 `check_information_integrity.py`의 정적 자료 검사로 구분한다. 실제 원문 일치·사유 선택의 정확성·동시 수정 처리 동작은 검사하지 않는다.

## 추가 자료 관계와 검증 완료

[정적 무결성 검사](static-integrity.md)에 식별 키의 유일성 범위, 모든 예시의 검사 범위, 저장 전달 타입 관계 및 검증 완료 파일의 항목별 필요 이유를 설명한다. `source_manifest.json`의 버전·해시 일치는 생성 기준 확인이며 전체 성공의 증거는 아니다. 전체 검증 후 `python3 verify.py --check`로 마지막 성공 결과가 현재 파일에 유효한지 확인한다.
